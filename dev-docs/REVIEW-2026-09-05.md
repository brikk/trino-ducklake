## Findings First

**RV-A01** (overall assessment): **There is substantial, useful engineering here, but I would not describe this revision as
generally production-safe for mixed-engine writes and destructive maintenance.** The main risks
are not stylistic: deleting a still-referenced physical file, changing historical/defaulted
values during rewrites, publishing incorrect statistics, and bypassing guarantees in alternate
entry points. The test harness can also report green without proving the intended Trino coverage.

The recent fixes are real improvements. This is not a recommendation to rewrite the connector.
It is a recommendation to finish the safety contracts before expanding the support matrix.

Priority and evidence conventions:

- **P1:** security exposure, possible data loss, silent wrong results, or a major supported-operation failure.
- **P2:** bounded-feature failure, resource/operational risk, misleading guarantees, or important coverage weakness.
- **P3:** maintainability, diagnostics, documentation, and genuinely low-risk cleanup.
- **Reproduced:** a focused executable probe demonstrated the stated component behavior during this review.
- **Source-confirmed:** the defect follows from the inspected implementation; its complete SQL/filesystem scenario was not executed here.
- **Needs reproduction:** a credible risk whose reachability or full consequence still needs a controlled test.

P1 is not a claim that every deployment is affected. Preconditions matter, especially permissions,
cross-engine concurrency, storage aliases, and particular physical type encodings.

## Security And Deletion

### RV-01: Catalog Password Is Not Redacted

**Status: completed 2026-09-05, commit `0036a10`.** Added `@ConfigSecuritySensitive` to the password
setter. `TestDucklakeConfig.testCatalogPasswordIsRedactedInConfigurationInspection` failed on
the original code and now confirms both reported values are `[REDACTED]`, while the config and
catalog config retain the actual synthetic credential. `RV-X14` remains separate and open.
See `RV-V08` for verification. The original finding follows.

**P1, reproduced at the configuration-inspection boundary.**
`S/DucklakeConfig.kt:69-76`; `S/DucklakeConnectorFactory.kt:45-60`.

The password setter lacks `@ConfigSecuritySensitive`. A probe registered this config with the
pinned Airlift library, supplied a deliberately fake password, and read it back from
`ConfigurationInspector.ConfigAttribute.currentValue` verbatim, not redacted. Bootstrap uses
this configuration machinery; normal configuration logging can expose the catalog credential.
`doNotInitializeLogging()` is not a password-redaction setting.

Add the annotation and a configuration-inspector regression using a synthetic secret. Review
credential-bearing JDBC URLs as a separate configuration concern (`RV-X14`). No real credentials or
production logs were inspected in this review.

### RV-02: Procedure Permission Does Not Enforce Target-Table Permission

**P1, source-confirmed; restricted-principal integration test still required.**
`S/DucklakeAddFilesProcedure.kt:109-118,137-193`;
`S/DucklakeRewriteDataFilesProcedure.kt:121-138`;
`S/DucklakeFlushInlinedDataProcedure.kt:103-124`.

These procedures do not request the `ConnectorAccessControl` that Trino 483 can inject. Trino's
CALL executor checks permission to execute the procedure, not INSERT or maintenance permission
on the table supplied as a string argument. A user granted `system.add_files` can consequently
target a table on which ordinary INSERT is denied. With shared storage credentials, arbitrary
file import can also expose data through a different readable table.

Check the relevant target-table permission before catalog/filesystem work. Treat catalog-wide
expiry and deletion as explicitly administrative operations. Test EXECUTE-allowed/table-write-
denied principals; document that raw-path import is a powerful storage-level capability.

### RV-03: Equivalent Path Spellings Can Turn Live Files Into Orphans

**P1, source-confirmed; existing P-M4 deserves higher priority.**
`S/DucklakeRemoveOrphanFilesProcedure.kt:276-280,313-325`;
`S/DucklakePathResolver.kt:44-49,65-70`.

Known-file protection uses string equality. `Location.of(path).toString()` preserves the spelling;
it is not normalization. An aged managed file registered as `file:///warehouse/t/ducklake-x.parquet`
can be listed as `/warehouse/t/ducklake-x.parquet`, fail membership, and be deleted while live.
The repaired global retained-owner hierarchy does not fix filesystem aliases.

Use a backend-aware comparison identity at registration, ownership lookup, and listing. Do not
indiscriminately normalize object-key slashes or escapes. Add mixed bare/file-URI tests to
`TestDucklakeRemoveOrphanFiles`; the present retained-owner tests use consistent spellings.

### RV-04: Scheduled Cleanup Is Not Safe for Shared Physical Ownership

**P1, source-confirmed across the catalog boundary.**
`S/DucklakeAddFilesProcedure.kt:192-193,307-317`;
`S/DucklakeCleanupOldFilesProcedure.kt:79-107`;
`C/JdbcDucklakeCatalog.kt:889-910,1155-1172,4293-4302`.

`add_files` allows two tables to reference the same file. Expiration schedules retired file IDs,
then cleanup deletes their paths without protecting another retained owner of that path. Import
a source table's file into a destination, drop/expire the source, and cleanup can destroy the
destination's live data. `T/TestDucklakeAddFiles.kt:104-132` already uses shared-file registration,
but does not exercise subsequent ownership retirement.

Define physical ownership explicitly: either reject conflicting registrations or coordinate
reference-aware scheduling/deletion across all retained owners. Include already-scheduled paths
and concurrent registration. A non-atomic last-second existence check is not the whole fix.

### RV-05: Empty-Directory Cleanup Has a Destructive Race

**Status: completed 2026-09-05, commit `b83fa4f`; also closes P-L6.** Removed the post-delete
directory sweep and its helpers. Only selected orphan files are deleted; empty directories are
retained. `TestDucklakeRemoveOrphanFiles.keepsFileCreatedAfterEmptyDirectoryListing` deterministically
captures an empty listing, creates a new file, and checks that it survives with zero recursive
directory deletions. It failed on the original code because the new file was deleted.
`reclaimsOrphanDatasetFilesButKeepsDirectories` also verifies that aged legacy dataset members
are reclaimed while their directories remain. See `RV-V08`. `RV-03`, `RV-04`, and `RV-X03` are
not closed by this fix. The original finding follows.

**P1, source-confirmed race; existing P-L6 is not merely cosmetic.**
`S/DucklakeRemoveOrphanFilesProcedure.kt:180,197-228`.

After deleting selected files, the procedure lists an intermediate directory, then recursively
deletes it if the listing was empty. At catalog/schema scope that directory can be a schema/table
directory, not just an old Lance dataset. A writer can create a file between the check and the
recursive delete. That new file bypasses the age, ownership, and managed-filename protections.

Prefer leaving directory shells. If removal is necessary, use an atomic non-recursive
empty-directory operation where supported. The current comment claiming this can never remove
live data is false. Add a filesystem test that creates a file between check and deletion.

## History And Transactions

### RV-06: Partial Rewrite Loses Dropped-Column History

**P1, source-confirmed.**
`S/DucklakeRewriteDataFilesProcedure.kt:162-166,241-249,364-369,408-420`;
`C/JdbcDucklakeCatalog.kt:4732-4746`.

Partial rewrite projects the current schema, backdates its output, and removes the source-file
metadata. If retained older snapshots had a subsequently dropped column, the replacement file
does not contain that column. Historical values become NULL, and later cleanup removes the
original physical evidence. Dropped nested fields have the same underlying problem.

This is separate from P-H2, whose delete-bearing-source exclusion is present. The partial-rewrite
test at `T/TestDucklakeRewriteDataFiles.kt:395-423` keeps one unchanged column throughout.
Preserve the historical physical schemas, or explicitly refuse partial replacement when that
history cannot be represented losslessly. Ordinary rewrite can retain older source versions.

### RV-07: Ordinary Rewrite Replaces Initial Defaults With NULL

**P1, source-confirmed.**
`S/DucklakeRewriteDataFilesProcedure.kt:162-166`;
`S/DucklakePageSourceProvider.kt:1542-1556`.

Rewrite builds column handles without `initialDefault`; ordinary handle construction supplies
it at `S/DucklakeMetadata.kt:376-383`. After another engine adds `b INTEGER DEFAULT 42`, SELECT
can correctly project 42 from older files, but compaction reads those files with default-less
handles and writes physical NULLs. This changes latest-table values, not just time travel.

Carry the same initial-default metadata as normal reads. Add a before/after cross-engine rewrite
test containing both pre-ADD files and post-ADD files, with explicit NULLs as a control.

### RV-08: Read-Snapshot Conflict Checks Miss Concurrent Inlined File Deletes

**P1, source-confirmed validation gap; race outcome needs a barrier-controlled reproduction.**
`S/DucklakeMetadata.kt:1419-1430`;
`S/DucklakeRewriteDataFilesProcedure.kt:275-279`;
`C/JdbcDucklakeCatalog.kt:4822-4856,4963-4972,2527-2530,2561-2573`.

Passing `readSnapshotId` is fixed. However, the dependency's stale-delete guards inspect physical
delete-file metadata, not newer inlined deletions of file-resident rows. Its general conflict
window begins when the catalog commit attempt starts, after materialization.

If DuckDB commits an inlined deletion after Trino reads but before Trino starts its commit,
UPDATE can publish a replacement for that deleted row, or rewrite can retire its source and
publish the stale row. Checking pre-existing inlined deletes during candidate selection does
not cover this window. This also strengthens the older P-L3 concern.

The catalog must validate newer inlined file deletes in the same transaction as commit, on every
attempt, for all touched source IDs. Test UPDATE and both rewrite modes against a paused
cross-engine inlined DELETE. Do not label TR-8's completed parameter plumbing itself unfixed.

### RV-09: Serializable Is Advertised Without a Pinned Transaction Snapshot

**P1, source-confirmed.**
`S/DucklakeConnector.kt:100-104`;
`S/DucklakeMetadataFactory.kt:33-35`;
`S/DucklakeSnapshotResolver.kt:55-85`.

The connector accepts SERIALIZABLE, but resolves the default current snapshot repeatedly rather
than pinning it per transaction. Repeated reads can see different committed states; separate
table resolutions can straddle a commit. Session/configuration snapshot-pin tests do not prove
transaction isolation.

Pin the appropriate default snapshot in transaction/query state and reject isolation guarantees
not implemented. Preserve explicit time-travel overrides. **RV-09a** is this snapshot/isolation
claim. Separately, **RV-09b** (existing TR-10) is coherent planning:
`S/DucklakeSplitManager.kt:82-96,123-163` performs independent catalog reads without `readSession`.
A numeric snapshot alone does not make representation-changing metadata reads coherent. Use a
scoped planning batch, not an imagined JDBC transaction spanning coordinator-to-worker callbacks.

**Important correction:** W-M6's old claim that multi-statement writes silently autocommit is
incorrect for Trino 483. `Connector.isSingleStatementWritesOnly()` defaults to true; Trino refuses
those writes. That is not the same issue as the unsupported read-isolation promise.

### RV-10: Name-Based DROP/TRUNCATE Can Mutate a Replacement Table

**P1, source-confirmed.**
`S/DucklakeMetadata.kt:814-824`;
`C/JdbcDucklakeCatalog.kt:3190-3192,3286-3288`.

The bound handle's table ID is discarded in favor of name-based catalog mutation. If A is
dropped and B is created under the same name between binding and mutation, the operation can
drop/truncate B. Historical snapshot pins also produce stale identities without a tiny race window.

Pass an expected table ID into an atomic catalog operation. A connector-only pre-check still
races. Test name reuse after binding and DDL with an old configured/session snapshot.

### RV-11: CTAS and View Replacement Publish Partial Operations

**P1, source-confirmed; CTAS is existing W-M5.**
`S/DucklakeMetadata.kt:1113-1127,1182-1193,1519-1542`;
`S/DucklakeTransactionManager.kt:42-55`.

**RV-11a:** CTAS publishes CREATE before writing/committing data. A failing query leaves an empty table and
other clients can observe it before completion. **RV-11b:** CREATE OR REPLACE VIEW similarly drops the old
view before encoding/creating the replacement; failure loses the active definition and creates
a name-claim race. An atomic metadata replacement API is already used for view comments at
`S/DucklakeMetadata.kt:1623-1634`.

Make each operation one catalog publication. Dropping a failed CTAS table afterward is cleanup,
not atomic visibility, and needs identity protection itself. Add failure-injection and concurrent-
reader tests; current successful CTAS/view-replacement tests cannot establish these contracts.

### RV-12: MERGE's Synthetic Position Ranges Reject Valid Lineage Layouts

**P1 supported-operation failure, source-confirmed design limitation; full fixture still needed.**
`S/DucklakeMetadata.kt:1284-1295`;
`S/DucklakeUpdatePartitioningHandle.kt:33-39`;
`S/DucklakePageSourceProvider.kt:1669-1675,1725-1727`.

MERGE identifies a source position as `rowIdStart + physicalPosition` and requires those ranges
not to overlap. A lineage-preserving replacement of files A `[0,2)` and C `[4,6)` may contain
embedded IDs `[0,1,4,5]`, start at 0, and have four rows while B `[2,4)` remains active. Actual
row identities are disjoint; the synthetic ranges overlap, so DML is rejected.

The overlap guard prevents ambiguous deletion and must not simply be removed. Use explicit
source-file identity plus file-local position for MERGE routing. Add a noncontiguous-source
rewrite fixture followed by DELETE/UPDATE/MERGE; the current partitioning test rejects overlap
without questioning whether valid storage can produce it.

## Read And Type Contracts

### RV-13: Nested Projection Still Confuses Identity and Nullness

**P1, source-confirmed; a residual R-H3/R-H5 edge, not a missing dependency upgrade.**
`S/DucklakeParquetTypeUtils.kt:87-103,183-200`;
`S/DucklakePageSourceProvider.kt:1251-1254`.

Two separate regressions need coverage:

- **RV-13a:** For mapped imported files, a missing nested mapping falls back to the current name. Import
  `s.x`, drop it, and add a new `s.x`: the new identity can read the old physical value. The
  fallback still cites catalog 0.7.2, despite the 0.8.0 nested-map adoption. An authoritative
  map miss must mean absent, not permission to guess by name.
- **RV-13b:** If none of a struct's current children exists physically, the entire struct becomes NULL.
  A non-NULL old `ROW(a)` after adding `b` and dropping `a` should retain parent nullness with
  `b = NULL`. Preserve definition-level information rather than synthesizing a NULL parent.

The identity tests cover ordinary drop/readd and mapped renames, but not mapped drop/readd or
removing every original struct child. These are combination gaps around otherwise good fixes.

### RV-14: Change Feed Does Not Reuse the Full Normal-Scan Contract

**P1 for wrong values, source-confirmed.**
`S/DucklakePageSourceProvider.kt:530-543,617-624,924-960`;
`S/AbstractChangeFeedTableFunction.kt:101-106`.

Subclaims: **RV-14a** file name/identity mappings; **RV-14b** partition constants;
**RV-14c** initial defaults; **RV-14d** inline schema-era conversion; **RV-14e** encryption admission.

`openChangeFeedFile` synthesizes a split with empty name mappings and partition constants.
Imported files whose source IDs differ from target IDs can therefore be bound incorrectly;
Hive files omitting their partition column can return NULL instead of the path/catalog value.
Feed handles also omit initial defaults, and inlined event conversion bypasses ordinary
schema-era/nested-identity conversion.

Preserve historical per-file mappings, constants, defaults, and inline schema provenance.
Test feeds over imported reordered columns, omitted partition columns, old-schema defaults,
and inlined nested renames. The existing feed test adding a nullable column is insufficient.

The normal encrypted-table gate is also bypassed by feed analysis/special-split dispatch
(`S/AbstractChangeFeedTableFunction.kt:89-119`; provider `:1344-1347`). This is an unsupported-read
policy gap, not evidence that encrypted Parquet can be decrypted. Apply admission checks to
every data-bearing entry point while preserving diagnostic metadata access.

### RV-15: Consolidated Puffin History Is Flattened

**P1, source-confirmed; R-M7 needs a corrected description.**
`S/DucklakePageSourceProvider.kt:763-787,969-1002`;
`S/DucklakeFlushInlinedDataProcedure.kt:283-298,311-313`;
`S/DucklakePuffinDeleteReader.kt:79-115`.

Ordinary Puffin time-travel filtering understands per-blob snapshots. **RV-15a:** Change feed instead unions
positions and attributes them to one deletion snapshot. **RV-15b:** Flush likewise unions existing Puffin
positions and tags all of them with the file's earliest begin snapshot. If A was deleted at S2
and B at S3, flushing can make B disappear at S2; narrow change-feed windows are also wrong.

Expose position-to-earliest-deletion-snapshot data from the Puffin reader and preserve it in both
consumers. Use catalog begin snapshot only for genuinely untagged blobs. Add consolidated-Puffin
feed-window and flush-history tests. HEAD no longer sends these files blindly to the Parquet
reader, so the previous R-M7 crash explanation must not be repeated.

### RV-16: Partition Import Has Multiple Representations of the Same Value

**P1, source-confirmed; distinct from the completed P-H3 coverage check.**
`S/DucklakeAddFilesProcedure.kt:488-504`;
`S/DucklakeAddFilesNameMapper.kt:195-204,215-218`;
`S/DucklakeSplitManager.kt:488-502,527-530,773-800,843-850`.

Subclaims: **RV-16a** escaped-value mismatch; **RV-16b** NULL sentinel stored as text;
**RV-16c** empty values skipped; **RV-16d** explicit NULL confused with absence;
**RV-16e** invalid typed values accepted.

Registration stores raw Hive path values, projection decodes them, and pruning consumes catalog
values. `region=us%20east` can project `us east` but be pruned for that same predicate. The Hive
NULL sentinel is registered as text rather than logical NULL. Empty `key=` values are skipped
by path parsing. Other paths omit explicit NULL constants, confusing them with absent values
eligible for initial-default substitution. Invalid typed values can reach parse-to-NULL fallback.

Use one decoding/canonicalization contract for registration, projection, and pruning, preserving
three states: absent, explicit NULL, and empty string. Validate before registration. Test escaped
values, NULL sentinels, empty values, invalid numerics, and non-NULL defaults, including predicates.

### RV-17: Defaults Are Wrong on Both New Writes and Old-File Projection

**P1, source-confirmed.**
`S/DucklakeMetadata.kt:280-287`;
`C/DucklakeColumn.kt:24-39`;
`S/DucklakePageSourceProvider.kt:294-301,1549-1562`;
`S/InlinedNestedFieldMapping.kt:123-128`.

**RV-17a:** Current INSERT defaults are not exposed through `ColumnMetadata`. For a DuckDB-created
`b INTEGER DEFAULT 42`, Trino `INSERT INTO t(id) VALUES (1)` supplies NULL for omitted `b`.
The catalog payload exposes initial defaults, not the current default and its dialect; these
must not be conflated.

**RV-17b:** Separately, old-file/inlined projection catches unsupported initial-default parsing and returns

conservative partition-pruning parser for value projection is the wrong failure contract.

Expose/translate supported current defaults for INSERT; decode initial defaults correctly or
fail with column/value context. Test omission versus explicit NULL and old versus new files.

### RV-19: Unsigned Validation Stops at Top-Level Channels

**P1, source-confirmed.**
`S/DucklakeUnsignedRangeChecker.kt:185-234`;

**RV-19a:** Scalar range checks are good, but the validator never descends through ROW/ARRAY/MAP. A

### RV-20: Statistics Still Contain Incorrect Bounds

**P1, reproduced component defects; distinct from completed W-H1/W-H3/P-H4 fixes.**
`S/DucklakeStatsExtractor.kt:119-129,164`;
`S/DucklakeAddFilesTypeChecker.kt:94-96`.

Two direct probes against the current compiled implementation produced:

| ID | Input | Actual emitted bounds | Correct contract |
|---|---|---|---|
| **RV-20a** | DOUBLE row groups `[-Infinity,-2]` and `[-1,-0.5]` | min `-1.0`, max `-0.5` | Retain negative infinity or emit unknown bounds, never exclude real values. |
| **RV-20b** | Physical DECIMAL(10,2), unscaled `12345`, imported as DECIMAL(12,4) | min/max `1.2345` | Numeric value `123.4500`. |

The infinity bug comes from the legacy numeric-Boolean comparator falling back to lexical order
when BigDecimal cannot parse infinity. Decimal decoding uses target scale instead of the source
annotation. These bounds can mislead downstream pruning even while current Trino catalog-stat
pruning is poorly connected to the planner. **RV-20c** (needs reproduction): BCE/wide-year lexical temporal ordering also needs
an edge-case test; canonical formatting alone does not establish chronological comparison.

Use typed comparison with unknown propagation and decode source scale before conversion. **RV-20d:** Check
decimal compatibility by available integral digits too: independent precision/scale inequalities
can accept a target that cannot contain the source's full range. Existing decimal import tests
use equal scales and miss this path.

### RV-21: Bucket Encoding Is Not DuckLake Hash Parity

**P1 for cross-engine partition correctness, source-confirmed encoding mismatch.**
`S/DucklakePartitionComputer.kt:272-295,317-321`;
`ducklake/src/functions/ducklake_murmur3.cpp:52-55,88-93`.

Subclaims: **RV-21a** timestamp units; **RV-21b** UUID representation; **RV-21c** unsigned representation.

The connector hashes microseconds for every timestamp precision and UUID bytes, while upstream
uses the stored integer representation or textual fallback. Unsigned physical types also require
their original type information rather than hashing the widened signed Trino representation.
Wrong bucket metadata can make a foreign engine prune matching rows.

Carry the DuckLake type into writing and matching; verify against DuckDB, not only Iceberg
reference vectors. The current signed integer/string/date hash tests do not establish full parity.
Qualify read-side impact: bucket-only predicates are currently NOT_ENFORCED and normally do not
reach this pruner; mixed transforms can expose it. Do not claim every Trino bucket predicate
currently under-returns. Non-UTC TIMESTAMPTZ temporal pruning is a separate reproduction target.

### RV-22: Malformed Delete/Lineage Data Can Fail Open

## Operations And Scale

### RV-23: The Negative Lineage Cache Reopens and Leaks Inputs

**P2, source-confirmed; potentially severe for large first UPDATEs.**
`S/DucklakeMergeSink.kt:150,164-175`;
`S/DucklakeDeleteFileReader.kt:175-199`.

**RV-23a:** Kotlin `getOrPut` recomputes when the stored value is null. Ordinary files without embedded

### RV-24: Output Ownership Does Not Survive Failure Through Commit

**P2, source-confirmed; W-M4/P-M6 remain open.**
`S/DucklakePageSink.kt:393-400,422-438`;
`S/DucklakeMergeSink.kt:355-374,435-439`;
`S/DucklakeRewriteDataFilesProcedure.kt:187-201,378-383,422-426`;
`S/DucklakeFlushInlinedDataProcedure.kt:169-177,382-417`.

**RV-24a:** Ordinary sink abort deletes tracked data files, but coordinator commit rejection does not own a

abandoned. **RV-24b:** Streams are opened before writer construction enters a safe ownership scope; some
abort methods close but do not delete the object.

and handle ambiguous commit outcomes explicitly before deleting anything. Inject failures at
construction, write, close, later partition groups, and commit. Periodic orphan cleanup is a
fallback, not an atomic write lifecycle, particularly given RV-03 through RV-05.

### RV-26: Maintenance Can Return Success After Real Filesystem Failure

## Test Verdicts

### RV-28: Corpus Green Does Not Necessarily Mean Trino Was Checked

**P1 for validation integrity, source-confirmed.**
`T/TestTrinoCorpusReplay.kt:133-139`;
`T/TrinoReplayEngine.kt:126-137,178-195`;
`Q/ReplayDriver.kt:45-50,388-392,482-519`;
`Q/CorpusRunner.kt:85-90,115-118`.

Subclaims: **RV-28a** oracle passes counted as connector coverage; **RV-28b** refusal reasons/caps
not reported distinctly; **RV-28c** timeout verdict and lost outcomes; **RV-28d** broad runtime skips.

The assertion is empty failures/crashes and `totalPassed > 50`. However, queries not mirrored
retain their oracle Pass, including dialect refusals, open oracle transactions, and queries
beyond the first 40 mirrors per file. The Boolean adapter discards detailed refusal reasons.
An adapter declining every query can still meet the threshold. A watchdog timeout becomes a
TIMEOUT file skip with empty outcomes rather than a failing crash, losing accumulated outcomes.

Runtime string matching also converts broad errors such as `does not exist`, `not supported`,
`not registered`, and `Cannot apply operator` into engine skips. Those strings can describe a
regression in supported functionality, not a legitimate dialect exclusion.

Separate oracle passes, successful mirrors, declined/capped mirrors, runtime skips, and timeouts.
Require meaningful mirrored coverage per selected directory. Retain partial outcomes and fail
unexpected timeouts. Bind permitted runtime skips to identified cases and expected causes.
Add negative-control harness tests: all queries declined, supported table missing, unexpected
unsupported type, and a timeout after an earlier failure. More corpus volume is not the fix.

### RV-29: Live Mirror Comparison Erases Meaningful Differences

**P1 for validation integrity, source-confirmed comparator behavior.**
`Q/ReplayDriver.kt:504-519`; `Q/GoldenComparator.kt:198-209`.

Subclaims: **RV-29a** NULL/string collision; **RV-29b** empty/string collision;
**RV-29c** column-separator collision; **RV-29d** ignored ordering;
**RV-29e** types not compared; **RV-29f** lost temporal precision.

The comparator renders cells to golden strings, joins columns with a separator, and sorts every
result. It conflates SQL NULL with literal `"NULL"`, empty string with literal `"(empty)"`, and
can conflate column boundaries when a cell contains the separator. It ignores order even for
NOSORT results, does not compare types, and temporal rendering truncates nanoseconds to micros.

Use structured nullable typed cells for live-vs-live comparison; keep upstream golden formatting
as a separate operation. Test each collision, nanosecond differences, and ordered results. The
older read TODO proposes typed comparison, but the current implementation is not that design.

### RV-30: Required Fixtures Can Turn Into Successful Skips

**P2, source-confirmed CI coverage risk; no external CI result was inspected.**
`T/TestTrinoCorpusReplay.kt:84-98`;
`T/TestDucklakeS3ParquetEndToEnd.kt:90-107`;
`.github/workflows/corpus-nightly.yml:46-60`; `.github/workflows/ci.yml:84-93`.

Subclaims: **RV-30a** required nightly setup can skip; **RV-30b** S3 fixture failures/image drift
can skip; **RV-30c** green PR runs do not retain reports showing skips.
Within the S3 umbrella, **RV-30b1** is broad setup-exception-to-skip handling;
**RV-30b2** is the unpinned MinIO image and assumed in-image tooling.

remove coverage instead of failing. PR reports are uploaded only on failure, hiding green skips.

Permit optional local environments, but make explicitly provisioned CI workloads mandatory.
Preserve setup causes, pin fixtures, and publish coverage/skip summaries on success too. The
PostgreSQL fixture's narrower Docker-unavailable handling is a better model.

## Strengths

- **RV-S01: The production boundary is clearer.** A Parquet-only Trino data plane plus a released catalog
  library is easier to reason about than the former multi-format/embedded-engine design. The
  transpiler remains test-only; snapshot repositories are scoped and cannot shadow release pins.
- **RV-S02: Recent fixes address real invariants.** Stable field identity, nested catalog maps, sorted and
  deduplicated delete positions, one writer per source file, gross/live row-count distinction,
  physical timestamp units, and removal of the false sorted-scan guarantee are meaningful changes.
- **RV-S03: Flush history is substantially improved.** Historical schema versions, deleted inline rows,
  per-file row starts, physical drain, and materialization read snapshot are now handled. The
  Puffin attribution edge does not negate that work.
- **RV-S04: Interop is tested against another engine.** DuckDB read-back checks name maps, timestamps,
  lineage, survivor uniqueness, and historical visibility. This is much stronger than trusting
  connector self-round-trips or metadata rows alone.
- **RV-S05: Some regressions assert the physical preconditions.** Clearing `partial_max` on a real
  multi-snapshot delete file, forcing inline/Parquet modes, checking one active delete file, and
  deliberately omitting required markers are excellent patterns to extend.
- **RV-S06: Several safety defaults are good.** Expiration is separated from physical cleanup, retention
  floors exist, unknown unobserved NaN statistics remain unknown, unsupported formats are refused,
  and metadata-only inspection remains available for diagnosis.
- **RV-S07: Useful components already exist.** Path resolution, Hive codec, schema construction, leaf
  statistics projection, snapshot resolution, and view codec have focused homes. Most fixes can
  extend these instead of introducing another framework.
- **RV-S08: The work is documented candidly.** Stable issue IDs and dated closure notes make it possible
  to check whether a fix actually landed. The problem is reconciliation and authority, not a lack
  of engineering notes.

## Recommended Sequence

1. **Contain security and destructive risk (`RV-01` through `RV-05`).** Redact passwords, enforce permissions, make orphan
   comparison/deletion safe, and resolve shared-file ownership. Add tests before any automatic
   cleanup expansion.
2. **Protect values and history (`RV-06` through `RV-12`, `RV-15`, `RV-17`).** Fix rewrite defaults/history, Puffin attribution, source identity,
   and stale inlined-delete commit guards. Make CTAS/view replacement publication atomic.
3. **Make test green meaningful in parallel (`RV-28` through `RV-30`).** Repair mirror accounting/comparison, unexpected
   skip/timeout handling, and required CI fixtures. Do not wait for a larger full-corpus run.
4. **Close physical support contracts (`RV-13`/`RV-14`, `RV-16`, `RV-18` through `RV-22`).** Build a bidirectional inline/Parquet/type/promotion matrix;
   fix unsigned/nested validation, source-scale statistics, infinities, and partition encodings.
   Refuse unsupported semantics clearly until the corresponding path really works.
5. **Bound and simplify (`RV-23` through `RV-27`, `RV-N*`, `RV-Q11`, `RV-D*`).** Fix the negative lineage cache first, then output ownership, memory
   growth, metrics, and narrowly chosen extractions. Reconcile README and the existing trackers.

Do not combine these into one broad refactor. Each family deserves a small regression with
physical preconditions and, for interoperability, an actual DuckDB observer. Large architectural
workarounds, shared-storage scratch schemes, semantic degradation, or new skips require an
explicit decision rather than being smuggled into a cleanup patch.
